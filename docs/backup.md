# Резервные копии

Что копируется: **база Postgres** (паспорта, источники, тарифы, пользователи, база знаний RAG) и **том `uploads`** (сами файлы, которые загрузили студенты). Держать нужно оба: в базе хранятся только ссылка на файл и извлечённый из него текст, поэтому без тома записи о материалах останутся без файлов, а без базы файлы не к чему привязать.

## Как это устроено

Сервис `backup` в `docker-compose.yml` (профиль `prod`, только на сервере) запускает `deploy/backup.sh`:

- первая копия делается сразу при запуске контейнера, дальше — раз в сутки (`BACKUP_INTERVAL_HOURS`);
- одна копия — два файла с общей отметкой времени (UTC) в папке `backups/` рядом с `docker-compose.yml`:
  - `db-ГГГГММДД-ЧЧММСС.dump` — `pg_dump` в формате custom;
  - `uploads-ГГГГММДД-ЧЧММСС.tgz` — архив всего тома загрузок;
- файлы пишутся под временным именем и переименовываются только после успеха, пустой дамп считается сбоем;
- копии старше 14 дней (`BACKUP_KEEP_DAYS`) удаляются, но только после удачной новой копии: при серии сбоев последние рабочие копии не пропадут;
- `backups/last-success` — время последней удачной копии.

Настройка необязательна: значения по умолчанию подходят. Чтобы изменить, добавьте `BACKUP_INTERVAL_HOURS` и `BACKUP_KEEP_DAYS` в секрет `ENV_FILE` (попадёт в `.env` на сервере при следующей выкладке).

## Проверить, что копии делаются

```bash
cd <DEPLOY_PATH>
ls -lh backups/                      # db-*.dump и uploads-*.tgz свежих дат
cat backups/last-success             # время последней удачной копии (UTC)
docker compose -f docker-compose.yml -f docker-compose.prod.yml --profile prod logs --tail 20 backup
```

Сбой копии **не останавливает выкладку сайта**: у сервиса нет healthcheck намеренно. Поэтому сам он о проблеме не сообщит, `last-success` стоит иногда смотреть (или повесить на него мониторинг).

## Восстановление

Берите `db-…` и `uploads-…` с одной отметкой времени.

```bash
cd <DEPLOY_PATH>
COMPOSE="docker compose -f docker-compose.yml -f docker-compose.prod.yml --profile prod"

# 1. Остановить запись в базу и в том
$COMPOSE stop pipeline

# 2. База: объекты в базе заменяются содержимым копии
$COMPOSE exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists --no-owner' < backups/db-<отметка>.dump

# 3. Файлы: распаковываются поверх тома (то, чего нет в архиве, не удаляется)
docker run --rm -v passport-constructor_uploads:/data/uploads -v "$PWD/backups":/backups:ro alpine \
  tar -xzf /backups/uploads-<отметка>.tgz -C /data/uploads

# 4. Запустить обратно
$COMPOSE start pipeline
```

Имя тома — `passport-constructor_uploads` (проект `passport-constructor` из `docker-compose.yml`); `docker volume ls` покажет точное.

**Что проверено, а что нет.** Скрипт копирования проверен тестами (`backend/pipeline-api/tests/backup-script.test.ts`): создание, откат при сбое, ротация, архив распаковывается с тем же содержимым. Сама процедура восстановления базы на настоящем Postgres **не проверялась**. Прежде чем на неё рассчитывать, один раз прогоните её на копии: поднимите отдельный Postgres, выполните шаг 2 и проверьте, что паспорта и тарифы на месте.

## Чего эта защита не даёт

Копии лежат на том же диске, что и база. Они спасают от ошибки (удалили файл, испортили данные, неудачная миграция), но **не от потери сервера или диска**: вместе с сервером пропадут и копии. Для этого нужна копия на другой машине или в облачном хранилище, например `rsync` папки `backups/` по расписанию. Куда складывать, решает владелец; пока не настроено.

Свободное место: копия базы и архив файлов растут вместе с данными, за 14 дней хранится до 14 пар файлов. Место на диске сервера стоит иногда проверять.
