# Резервные копии

Короткая схема: `backup` делает копии на сервере → `backup-sync` шифрует их и отправляет в Backblaze B2.

Что копируется: **база Postgres** (паспорта, источники, тарифы, пользователи, база знаний RAG) и **том `uploads`** (сами файлы, которые загрузили студенты). Держать нужно оба: в базе хранятся только ссылка на файл и извлечённый из него текст, поэтому без тома записи о материалах останутся без файлов, а без базы файлы не к чему привязать.

## Как это устроено

Сервис `backup` в `docker-compose.yml` (профиль `prod`, только на сервере) запускает `deploy/backup.sh`:

- первая копия делается сразу при запуске контейнера, дальше — раз в сутки (`BACKUP_INTERVAL_HOURS`);
- одна копия — два файла с общей отметкой времени (UTC) в папке `backups/` рядом с `docker-compose.yml`:
  - `db-ГГГГММДД-ЧЧММСС.dump` — `pg_dump` в формате custom;
  - `uploads-ГГГГММДД-ЧЧММСС.tgz` — архив всего тома загрузок;
- файлы пишутся под временным именем и переименовываются только после успеха, пустой дамп считается сбоем;
- копии старше 14 дней (`BACKUP_KEEP_DAYS`) удаляются, но только после удачной новой копии: при серии сбоев последние рабочие копии не пропадут;
- `backups/last-success` — время последней удачной копии.

Настройка необязательна: значения по умолчанию подходят. Чтобы изменить, добавьте `BACKUP_INTERVAL_HOURS` и `BACKUP_KEEP_DAYS` в секрет `ENV_FILE` (попадёт в `.env` на сервере при следующей выкладке).

## Проверить, что копии делаются

```bash
cd <DEPLOY_PATH>
ls -lh backups/                      # db-*.dump и uploads-*.tgz свежих дат
cat backups/last-success             # время последней удачной копии (UTC)
docker compose -f docker-compose.yml -f docker-compose.prod.yml --profile prod logs --tail 20 backup
```

Сбой копии **не останавливает выкладку сайта**: у сервиса нет healthcheck намеренно. Поэтому сам он о проблеме не сообщит, `last-success` стоит иногда смотреть (или повесить на него мониторинг).

## Восстановление

Берите `db-…` и `uploads-…` с одной отметкой времени.

```bash
cd <DEPLOY_PATH>
COMPOSE="docker compose -f docker-compose.yml -f docker-compose.prod.yml --profile prod"

# 1. Остановить запись в базу и в том
$COMPOSE stop pipeline

# 2. База: объекты в базе заменяются содержимым копии
$COMPOSE exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists --no-owner' < backups/db-<отметка>.dump

# 3. Файлы: распаковываются поверх тома (то, чего нет в архиве, не удаляется)
docker run --rm -v passport-constructor_uploads:/data/uploads -v "$PWD/backups":/backups:ro alpine \
  tar -xzf /backups/uploads-<отметка>.tgz -C /data/uploads

# 4. Запустить обратно
$COMPOSE start pipeline
```

Имя тома — `passport-constructor_uploads` (проект `passport-constructor` из `docker-compose.yml`); `docker volume ls` покажет точное.

**Что проверено, а что нет.** Скрипт копирования проверен тестами (`backend/pipeline-api/tests/backup-script.test.ts`): создание, откат при сбое, ротация, архив распаковывается с тем же содержимым. Сама процедура восстановления базы на настоящем Postgres **не проверялась**. Прежде чем на неё рассчитывать, один раз прогоните её на копии: поднимите отдельный Postgres, выполните шаг 2 и проверьте, что паспорта и тарифы на месте.

## Копия вне сервера: Backblaze B2

Копии в `backups/` лежат на том же диске, что и база: они спасают от ошибки (удалили файл, испортили данные, неудачная миграция), но не от потери сервера. Поэтому сервис `backup-sync` (`deploy/backup-sync.sh`, образ `rclone/rclone`) отправляет их в приватный бакет Backblaze B2.

- Раз в 6 часов (`BACKUP_SYNC_INTERVAL_HOURS`), первая отправка через две минуты после запуска контейнера.
- **Шифрование на сервере** до отправки (rclone crypt): в Backblaze лежит только шифртекст, а пароль туда не попадает. Имена файлов не шифруются (в них только время копии), содержимое — да.
- Файлы **копируются, а не синхронизируются**: удаление старых копий на сервере не стирает их в бакете. Срок хранения в бакете задаёт правило жизненного цикла Backblaze (ниже).
- После отправки скрипт сверяет, что каждая локальная копия есть в бакете и совпадает по размеру. Результат — в логе контейнера.
- Ключ B2 привязан к одному бакету; конфигурация rclone задаётся переменными окружения и на диск не пишется.

### Настройка

Значения хранятся как секреты окружения `production` в GitHub (Settings → Environments → production); деплой кладёт их в `.env` на сервере:

| Секрет | Что это |
|---|---|
| `BACKUP_S3_ENDPOINT`, `BACKUP_S3_REGION`, `BACKUP_S3_BUCKET` | адрес S3 API, регион и имя бакета (страница бакета в Backblaze) |
| `BACKUP_S3_KEY_ID`, `BACKUP_S3_APPLICATION_KEY` | ключ приложения, привязанный к этому бакету |
| `BACKUP_ENCRYPTION_PASSWORD`, `BACKUP_ENCRYPTION_SALT` | пароль и соль шифрования копий |

Без этих секретов сервис ничего не отправляет и пишет в лог, каких переменных не хватает; копии остаются только на сервере.

> **Пароль и соль шифрования нельзя терять.** Без них копии в B2 расшифровать невозможно, а из GitHub секрет прочитать нельзя. Сохраните оба значения вне сервера и вне GitHub (менеджер паролей). Менять их после первой отправки нельзя: старые копии перестанут расшифровываться.

В Backblaze для бакета задайте правило жизненного цикла (Lifecycle Settings → custom): скрывать файлы через 30 дней, удалять через 1 день. Иначе при режиме «Keep all versions» старые копии будут копиться бесконечно. Ключу приложения достаточно прав `listBuckets`, `listFiles`, `readFiles`, `writeFiles`. Права на удаление и смену настроек бакета ему не нужны: без них скомпрометированный сервер не сможет стереть копии.

### Проверить, что выгрузка идёт

```bash
cd <DEPLOY_PATH>
COMPOSE="docker compose -f docker-compose.yml -f docker-compose.prod.yml --profile prod"
$COMPOSE logs --tail 20 backup-sync                    # «готово: копии … есть в бакете» либо «ОШИБКА …»
$COMPOSE run --rm backup-sync list                     # что лежит в бакете (имена и размеры расшифрованных файлов)
```

Если в логе написано «выгрузка в B2 не настроена, не заданы: …», нужного секрета нет в GitHub или деплой после его добавления ещё не выполнялся.

### Достать копию из бакета и расшифровать

```bash
mkdir -p restore
$COMPOSE run --rm -v "$PWD/restore:/restore" backup-sync fetch db-<отметка>.dump /restore
$COMPOSE run --rm -v "$PWD/restore:/restore" backup-sync fetch uploads-<отметка>.tgz /restore
```

Дальше — шаги 1–4 раздела «Восстановление», подставляя файлы из `restore/`. Если сервер потерян целиком: поднимите стек на новой машине (секреты B2 и шифрования возьмите из своего хранилища, а не из GitHub) и выполните те же команды. Без стека расшифровать можно и обычным `rclone`: те же переменные `RCLONE_CONFIG_B2S3_*` и `RCLONE_CONFIG_BCRYPT_*` (см. `setup_remotes` в `deploy/backup-sync.sh`).

**Что проверено, а что нет.** Скрипт выгрузки проверен тестами с подставным `rclone` (`backend/pipeline-api/tests/backup-sync-script.test.ts`): конфигурация, порядок действий, сбои, отсутствие секретов в логах. Реальная отправка в Backblaze с шифрованием и расшифровка **не проверялись**: настоящий `rclone` локально не запускался. Доступ к бакету по S3 (запись, чтение, листинг) проверен отдельно, но через собственный запрос, не через rclone. Поэтому после первой выкладки обязательно проверьте лог и `list`, а затем один раз скачайте копию через `fetch` и убедитесь, что она расшифровывается.

## Чего эта защита не даёт

- Пока в B2 не пошла первая успешная выгрузка, копии лежат только на сервере.
- Копия базы и копия файлов делаются подряд, а не в один момент: если студент загрузил файл между ними, в архиве может быть файл без записи в базе или наоборот. Для этого проекта это допустимо.
- Персональные данные в копиях, лежащих в зарубежном облаке (регион бакета — US East), остаются предметом вопроса к 152-ФЗ. Шифрование на сервере снижает риск утечки, но не отменяет требований закона. Это стоит сверить отдельно.

Свободное место: копия базы и архив файлов растут вместе с данными, за 14 дней на сервере хранится до 14 пар файлов. Место на диске сервера стоит иногда проверять.
